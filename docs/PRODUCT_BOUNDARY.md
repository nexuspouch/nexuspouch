# 产品边界：agent-hub（控制面）与 Nexuspouch（数据面）

> 状态：决策 v0.1（2026-08-02）
> 决策：**先只推 Nexuspouch 的"会话管理"故事；agent-hub 退为内部组件；
> 两个 Web UI 保持独立但边界写死；以深链打通，不合并**。

## 1. 决策摘要

- 差异化在数据面（会话内容可搜/可召回/可备份/本地管理），不在控制面；
- 单点突破优于双线作战：先让"会话管理中心"一个故事成立；
- hub 是内部组件（网关/接入通道），不独立对外推广；
- 两个 Web UI 独立：技术栈、部署形态、用户心智都不同；
- 未来若会话管理验证需求，再评估统一 "Agent Console"（不承诺）。

## 2. 分工边界（写死，双方 UI 不重复实现对方能力）

| | agent-hub（控制面） | Nexuspouch（数据面） |
|---|---|---|
| 层 | agents 怎么跑 | agents 产出了什么 |
| 管什么 | agent 实例、引擎、项目、启停、配对、隧道、**会话进程 resume/load** | **会话内容**：历史转写、搜索、语义召回、版本、备份、记忆 |
| 形态 | CLI + Web UI（桌面/开发工具） | 常开服务 + Web UI（节点） |
| 技术栈 | TS/Node | Rust |
| 用户 | 开发者 / 自托管玩家 | 更广的 agent 用户 |

### 关键概念区分（避免"两个 UI"混乱）

- **会话进程（hub）**：这个会话能不能恢复、在哪个进程/引擎里跑——生命周期；
- **会话内容（Nexuspouch）**：这个会话说了什么、能不能搜到/召回——数据资产；
- 两者同名"session"但不同层；文档与 UI 文案必须把这两个词讲清楚
  （界面可分别用"运行管理"与"会话与数据"区分心智）。

## 3. Web UI 边界

| UI | 拥有 | 不碰 |
|---|------|------|
| agent-hub UI | agents 列表、引擎、启停、项目、配对 QR、隧道状态、进程级 resume | 会话内容搜索/召回/版本 |
| Nexuspouch Web UI（P1.5） | 会话浏览/搜索/召回、产物、记忆、存储、绑定 | 进程管理、引擎启停 |

## 4. 深链集成（后置里程碑，不是现在）

- Nexuspouch 搜索结果 → "在 hub 中打开该会话进程"（深链）；
- hub 会话列表 → "查看历史内容"（跳 Nexuspouch 对应会话 URI）；
- 共享身份：device_id / agent_id 两边一致，一条心智、两个界面；
- 落地时机：Nexuspouch 会话 Web UI（P1.5）上线之后。

## 5. 未来合并评估（不承诺）

- 触发条件：会话管理验证需求（真机 QA / 用户留存数据）之后；
- 形态：统一 "Agent Console" 外壳——hub 作为控制面插件，Nexuspouch 作为
  数据面插件；不提前合并代码库。
